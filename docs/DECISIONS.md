# Parked decisions

Every genuinely-open business decision on this project. Work proceeds on the
stated default; nothing is silently guessed. Each affected line in the codebase
carries a `// TODO(D<n>): …` marker, so `rg "TODO\(D"` lists all open work.

**Protocol**

1. `src/config/site.ts` holds every unresolved value. Nothing else hardcodes them.
2. Resolving a decision should be a one-file change (plus deleting its TODOs).
3. New forks get a new row here before the code that assumes an answer is written.

Status legend: **OPEN** (default in force) · **RESOLVED** (answer applied) ·
**BLOCKING LAUNCH** (open item that must not ship as-is).

## D0 — Six real service pages instead of `/services#anchor`

The handoff links service bubbles to anchors on a single `/services` page and
lists "no individual service pages yet" as an intentional omission. **Overridden
by project direction:** six real pages at
`/services/{consulting,seasonal-planters,soil-testing,house-plants,garden-design,yard-maintenance}`,

`Service` schema. Anchors do not rank; these pages are the highest-value organic
lever on the project. `/services` becomes a real index page listing the six.

**Status:** RESOLVED — decided at kickoff.

## D7 — Turnstile keys and the no-JavaScript path

|                     |                                                                                                                                                                                                                                                                                                           |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Question**        | Cloudflare Turnstile is required on the contact form, but the form must also work with JavaScript disabled — and Turnstile's widget needs JavaScript to produce a token.                                                                                                                                  |
| **Proceeding with** | Honeypot + timing check are the JS-free floor and always run server-side. Turnstile is verified when a token is present and skipped when it is absent, so a no-JS submission still delivers. Keys come from env; with no keys configured the widget is not rendered and verification is skipped (dev/CI). |
| **Touches**         | `features/contact` server action, env schema, CSP if one is added.                                                                                                                                                                                                                                        |
| **On resolution**   | Supply `TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY`. If spam volume proves the honeypot insufficient, tighten to "token required" and accept that no-JS submissions break — that is a trade-off the client should make, not the build.                                                                   |
| **Status**          | OPEN · default in force                                                                                                                                                                                                                                                                                   |

## D10 — The GraphQL schema snapshot is unverified against a real space

|                     |                                                                                                                                                                                                                                                                                                                                         |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Question**        | Codegen runs against `src/lib/contentful/schema.graphql`, a hand-authored snapshot of the schema Contentful _will_ generate from the migration. No Contentful space exists yet, so it has never been checked against the real thing.                                                                                                    |
| **Proceeding with** | The snapshot models only the subset the app queries, follows Contentful's documented generated shape (`<type>Collection`, `<Type>Filter`, `<Type>Order`, `<Type><Field>` rich-text types), and marks model-required fields non-null.                                                                                                    |
| **Touches**         | Every generated type, and therefore every component built against them.                                                                                                                                                                                                                                                                 |
| **On resolution**   | Create the space, run the migration, then `CONTENTFUL_SCHEMA_FROM_API=1 npm run codegen`. Any drift surfaces immediately as a codegen or typecheck failure — which is the point of generating rather than hand-writing the types. Do this **before Phase 3 is finished**, so a nullability mismatch is a small fix rather than a sweep. |
| **Status**          | OPEN · needs a space to close                                                                                                                                                                                                                                                                                                           |

## D11 — 48px tap targets vs. the artboard's footer rhythm

|                           |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Question**              | The brief lists "tap targets ≥48px" under non-negotiable accessibility. The artboards set footer links at 17–18px on a 32px pitch, and section links like "See all my favorites →" as bare inline text — all well under 48px tall. Meeting the floor changes the footer's vertical rhythm.                                                                                                                                                                                                     |
| **Proceeding with**       | The floor wins. Every link that is a navigation target — header wordmark and phone, footer nav and contact, section "see all" links, card links, contact-band details — is `min-height: 48px` with the surrounding stack gap moved _into_ the link so 48px targets never overlap. Genuinely inline links inside a paragraph (the phone and email in the services intro) keep the line box: padding them would wreck the paragraph, and WCAG 2.5.8 exempts inline text for exactly that reason. |
| **Cost**                  | The full footer's link columns are roughly 80px taller than artboard 1b. Nothing else moves.                                                                                                                                                                                                                                                                                                                                                                                                   |
| **Why not the other way** | For a 45–75 audience reading outdoors on a phone, a 20px-tall link is the accessibility failure the brief is guarding against — and the brief ranks readability and obvious controls above visual trendiness explicitly.                                                                                                                                                                                                                                                                       |
| **On resolution**         | If the client wants the artboard footer exactly, the change is one class per link; `e2e/fidelity.spec.ts` will then need an exemption for footer links, which is the right place to record that trade-off.                                                                                                                                                                                                                                                                                     |
| **Status**                | DECIDED · deviation from the artboard, deliberately                                                                                                                                                                                                                                                                                                                                                                                                                                            |

## D13 — Content column widened beyond the artboards

|                              |                                                                                                                                                                                                                                                                      |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Question**                 | The artboards cap the content column at 1140px (1440) and 1280px (1920). On a 14-inch MacBook that leaves noticeably more empty margin than the design implies, because the artboards are snapshots at exactly 1440 and 1920 and most real laptops sit between them. |
| **Proceeding with**          | Client request: widen to **1260px at 1440 and 1440px at 1920** — `clamp(1260px, calc(720px + 37.5vw), 1440px)`. Backgrounds still bleed the full viewport; only the column inside them changed. At 1710px the column goes from 1218px to 1361px.                     |
| **Deliberately not widened** | The 860px article column on detail and service pages. Body copy is capped near 68ch for readability, which the brief ranks above visual preference — a wider prose column would be a regression for a 45–75 audience, not an improvement.                            |
| **Knock-on**                 | Six service bubbles at 250px would fit four across in a 1260px column, leaving a stranded row of two. The bubble row therefore keeps its own cap (`--container-bubbles`) so the staggered layout stays three across, as drawn.                                       |
| **Touches**                  | `--container-content` in `theme.css`; the anchors in `fluid-scale.test.ts` and `e2e/fidelity.spec.ts`.                                                                                                                                                               |
| **On resolution**            | Reverting to the artboard values is a one-line change plus those two test anchors.                                                                                                                                                                                   |
| **Status**                   | DECIDED · deviation from the artboards, at the client's request                                                                                                                                                                                                      |

## D14 — Making Contentful maintainable by a non-technical owner

|                        |                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Question**           | Edyta is not a technical specialist and will eventually maintain this site herself. Is Contentful workable for her, or does the project need a CMS with visual editing (Storyblok, Sanity Presentation)?                                                                                                                                                                                                                                     |
| **Proceeding with**    | Stay on Contentful and fix what actually makes a CMS hard for its owner, which is rarely the product. Every field now carries a plain-language label and help text written for her — "How much sun", not `lightTag` — set in the migration so it is versioned and repeatable. Field **ids** are unchanged, because the GraphQL queries depend on them; only what she reads changes.                                                          |
| **Still worth doing**  | A Contentful role that sees Content and nothing else — no API keys, no content model. _Custom roles are typically a paid tier, so check the plan before promising it._ Contentful Live Preview would add click-the-page-to-edit, which is the remaining gap between a form and a result. And a one-page guide with screenshots for the four things she will actually do.                                                                     |
| **Why not switch now** | Switching is contained but not free: components consume type aliases and everything CMS-specific sits behind `src/lib/contentful/`, so it is roughly Phase 1 redone plus re-authoring content. Paying that on a guess about what she will find hard is the wrong order. Put the labelled model in front of her with a real task first; if she stalls on the abstraction rather than the wording, that is the signal — and you will know why. |
| **Touches**            | `contentful/migrations/001-initial-content-model.cjs` only.                                                                                                                                                                                                                                                                                                                                                                                  |
| **Status**             | DECIDED · revisit after Edyta has tried it                                                                                                                                                                                                                                                                                                                                                                                                   |
